# CookLLM 功能开发规范（面向 Agent）

本文档约束 Agent 在 CookLLM 中新增或修改功能的落点、流程与验收标准。开始任务前先读本文与根目录 `AGENTS.md`；两者冲突时，以 `AGENTS.md` 的发布/提交规则为准。

## 一、基本原则

1. **先定位领域，再动手**：先读相关模块与调用链，确认改动落点，不要跨模块顺手重构。
2. **最小改动**：只实现当前需求，不新增抽象、不引入新依赖、不做无关格式化。需要新依赖时先说明理由并等待确认。
3. **行为兼容**：配置、下载任务、localStorage 中的历史数据必须能继续读取；新增字段一律可选并带默认值。
4. **真实可用**：禁止用 mock、占位实现或 TODO 代替功能；无法完成的部分要明确说明。
5. **高风险区先确认**：`Profile` 数据结构、配置 schema 的破坏性变更、i18n 全量改造、发布流程相关文件，必须先给出影响分析再动手。
6. **提交与发版分离**：代码改完不等于要发版。未明确要求时，不修改版本号、不写 CHANGELOG/README 更新日志、不提交、不打 Tag。

## 二、代码分层与落点

### 前端

| 位置 | 职责 | 新增内容时 |
| --- | --- | --- |
| `src/App.tsx` | 应用组合根：页面状态、生命周期、事件编排 | 只加编排代码；业务逻辑进 hooks |
| `src/hooks/useXxx.ts` | 按领域封装有状态逻辑（下载、服务控制、模型库、日志、引擎、更新、Toast） | 新领域新建 hook，沿用现有返回结构风格 |
| `src/components/` | 页面与复用组件；复杂页面拆分到子目录（`explore/`、`settings/`） | 页面组件只负责渲染与交互，数据处理放 hook |
| `src/styles/` | 按模块拆分的样式；入口 `src/index.css` 只做 `@import` | 新建样式文件并在 `index.css` 末尾按模块补 `@import` |
| `src/types.ts` | 前后端共享的领域类型与字面量联合类型 | 先在这里定义/复用类型，禁止在组件里重复定义联合类型 |
| `src/tauri.ts` | 所有 `invoke` 封装、前后端事件通信、浏览器环境降级 | 组件内不得直接 `invoke`，统一从这里导出函数 |
| `src/data.ts` | 默认参数模板、默认预设、版本迁移（`migrateConfig`）、示例数据 | 默认值/迁移只放这里，不散落到组件 |
| `src/i18n.ts` | zh / en 语言包与 `useI18n` | 新增用户可见文案必须同时补 zh、en 词条；复用已有 key 优先 |

补充规则：

- 新设 localStorage key 统一使用 `cookllm.` 前缀；读取时必须容错（`try/catch` + 类型/范围校验）。
- 新页面需要同步修改：`Page` 联合类型、`PAGE_LOG_MODE`、`Layout` 导航、`App.tsx` 页面分支、i18n 词条。
- 交互行为要覆盖键盘/鼠标、深色与浅色主题；复用现有 CSS 变量与控件样式，不另起一套视觉。

### Rust 后端

| 模块 | 负责范围 |
| --- | --- |
| `src-tauri/src/lib.rs` | 应用装配、命令注册、窗口/托盘生命周期；**只保留编排与装配** |
| `config.rs` | 配置结构、读写、备份导入导出、快捷键注册 |
| `process.rs` | 服务进程启停、状态、日志转发、孤进程清理 |
| `server_args.rs` | 启动参数构建（按引擎/预设生成命令行） |
| `engines.rs` | 引擎发现、目录扫描、安装与更新 |
| `downloads.rs` | HF / ModelScope 浏览、文件列表、下载、暂停/取消/续传 |
| `system.rs` | GPU、硬件、网络/代理检测 |
| `app_update.rs` | 应用自更新 |

补充规则：

- 新命令放到对应领域模块，并在 `lib.rs` 的 `tauri::generate_handler!` 中注册；不要把所有逻辑写回 `lib.rs`。
- 命令命名用 `动词_名词` 的 snake_case；前端参数按 Tauri 规则使用 camelCase。
- 前后端共享结构体使用 `#[serde(rename_all = "camelCase")]`；配置项新字段必须 `#[serde(default)]`（可选值再加 `skip_serializing_if`）。
- 错误返回与现有风格一致：普通命令 `Result<T, String>`；下载类沿用结构化错误类型。错误文案要能指导用户处理。
- 网络/磁盘等阻塞操作不要卡住 async 运行时；沿用模块内现有做法。
- 新增敏感字段（Token、密钥等）时，必须同步更新 `export_config_backup`，确保导出时不泄露。

## 三、新功能标准流程

1. **读代码**：确认现有调用链与数据流，列出要改的文件与影响面。
2. **定类型**：在 `src/types.ts` / Rust 结构体中定义字段与联合类型；新增配置项同步 `AppConfig`、`migrateConfig`、默认值。
3. **写后端**：在对应 Rust 模块实现命令 → 注册到 `lib.rs` → `cargo check`。
4. **封装接口**：在 `src/tauri.ts` 添加类型化 wrapper，处理非 Tauri 环境降级。
5. **写状态**：在合适 hook 中实现状态与副作用；组件不直接管理跨页面状态。
6. **写 UI**：组件 + i18n 词条 + 独立样式文件，并在 `index.css` 引入。
7. **自测**：跑通主路径与边界场景（空数据、失败重试、旧配置、重启后恢复）。
8. **验证门禁**：见第五节；全部通过后再汇报。

## 四、常见功能类型落点清单

### 新增页面

`Page` / `PAGE_LOG_MODE`（types.ts）→ `Layout` 导航 → `App.tsx` 分支 → 页面组件 → `styles/` 新文件 → i18n 词条。

### 新增 Tauri 命令

对应领域 `*.rs` → `lib.rs` 注册 → `tauri.ts` wrapper → hook 调用。命令入参/返回值必须显式类型化。

### 新增下载源

`CommunitySource` 等类型（types.ts）→ `downloads.rs`（trending/search/list/download 全套函数，沿用统一错误结构）→ `tauri.ts` → `useDownloads` 任务模型 → `ExplorePage` 来源切换与筛选 → 来源偏好 localStorage。

### 新增引擎类型

`EngineType`（types.ts）→ `engines.rs` 可执行文件识别/版本检测 → `server_args.rs` 参数分支 → `data.ts` 默认预设 → 设置页引擎卡片/弹窗 → i18n。新增后全局搜索 `EngineType` 与引擎名，确保所有分支覆盖。

### 新增配置项

`AppConfig`（types.ts + config.rs，serde 默认值）→ `migrateConfig`（data.ts）补默认值 → 设置页 UI → 保存链路。不得改变已有字段语义；删除/重命名字段必须提供迁移。

### 新增预设参数

`Profile`（types.ts + config.rs）→ `DEFAULT_PROFILES` / `DEFAULT_NINFER_PROFILES`（data.ts）→ `ProfileEditor` → `server_args.rs` 参数拼接 → i18n。可选字段才允许新增，默认值必须与引擎官方默认一致。

### 新增 localStorage 偏好

`cookllm.` 前缀 → 初始化时容错读取 → 变更时写入 → 导入/导出配置若需携带，纳入 `AppConfig` 而不是单独存 key。

### 新增快捷键 / 托盘项

快捷键：settings 快捷键录制 UI → `config.rs` 保存/注册 → `lib.rs` 生命周期；托盘：`lib.rs` 托盘菜单与事件处理，注意运行状态、模型切换、窗口恢复的一致性。

## 五、验证门禁（完成定义）

代码类改动至少执行：

```bash
npm run typecheck
npm test
cargo check --manifest-path src-tauri/Cargo.toml
```

按 `AGENTS.md` 要求，功能开发完成后还需执行完整本地打包：

```bash
npm run tauri build
```

同时满足：

- 主路径可用，边界场景（空数据、失败、旧配置、重启恢复）不崩溃；
- 没有新增控制台报错、Rust 警告中与本次改动相关的问题；
- 不残留调试代码、临时日志、无用依赖、未使用变量；
- 改动文件清单、验证结果、已知风险在汇报中写清楚。

## 六、提交与发布边界

- **仅文档/截图**：按 `AGENTS.md` 只提交推送，不改版本号、不编译、不打 Tag。
- **功能/代码改动**：完成并通过门禁后等待用户明确指令再提交；发版必须走 `npm run release:bump` + `npm run release -- --yes`，禁止手工逐个改版本号。
- 未明确要求时：不修改 `package.json`、`Cargo.toml`、`src/data.ts` 的版本号，不更新 CHANGELOG/README 更新日志，不执行 `git push` / `git tag`。
- 禁止破坏性 git 操作（`reset --hard`、`clean -f`、强制推送等），除非用户明确授权。

```text

约束：遵循 AGENTS.md 与 docs/开发规范.md；不新增依赖；不改版本号/CHANGELOG/README；不提交、不发版。
行为要求：
1. <主路径>
2. <边界场景>
3. <兼容要求：旧配置/旧任务/localStorage>
验收：
- npm run typecheck / npm test / cargo check 通过
- 手动验证：<具体步骤>
- 汇报改动文件、验证结果与风险点
```

复杂任务建议先让 Agent 输出「改动文件清单 + 实施步骤」，确认后再写代码，避免一次改太多导致难以回滚。
